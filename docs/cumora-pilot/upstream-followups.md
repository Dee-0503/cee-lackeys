## P1：官方 iOS App 对自托管后端的推送支持

- 创建日期：2026-09-20。
- 上游 Issue：https://github.com/yetone/cumora/issues/300
- 已核验状态：OPEN。
- 当前 pilot：Cumora v0.18.6；原生 iOS 自托管登录已由用户确认成功；APNs 未配置。
- 用户要求：等待官方支持后优先补齐能力；当前不为此自行维护 iOS fork。
- Issue 正文留档：[upstream-ios-push-issue.md](upstream-ios-push-issue.md)。未提交任何密钥、配对码、设备令牌、个人邮箱或私有部署地址。

### 跟进触发条件

每次 Cumora 升级评估、移动端问题排查和 pilot 恢复推进时，优先读取 #300 的回复、关联 PR 和正式 release notes。Issue 关闭本身不等于功能已发布；确认正式版本包含支持官方 App + 自托管后端的方案。

当前没有设置定时轮询或自动通知；不能承诺离线期间实时发现官方更新。GitHub 自身的 Issue 通知取决于用户账号设置。

### 官方支持后的实施清单

1. 核验支持路径、固定版本、账号/凭据所有权、费用与消息数据流；若仍要求自签 App，向用户报告而非默认为已满足需求。
2. 按官方方案准备 pilot 配置和备份，机密使用已有安全注入方式；新增第三方服务、账号授权或付费依赖单独落实。
3. 先解决原生插件加载/权限/令牌注册问题，再测试 APNs 发送；两者分别记录结果。
4. 验证应用后台、锁屏、点击通知返回正确自托管服务器/工作区/会话，以及注销后的令牌撤销。
5. 聊天消息推送与日历提醒推送分别验收；不能用前者成功宣称后者可用。
6. 记录失败重试、重复通知、回滚与禁用方法；人工确认后再标记能力通过。

### 当前排除项

不索取官方 APNs 私钥，不把自有 Apple key 当作可推送官方 Bundle ID 的凭据，不自动接入邮件/Telegram/ntfy 等替代通知，不修改 Wiki 或其他项目。
